Async/Await Under the Hood

Comparing today's compiler-generated state machines vs .NET 11 Preview 4's runtime async — a walkthrough for our sync major service.

Contents

1. Primer: what is a state machine?

Before we look at async/await specifically, it helps to be clear on what a state machine is and why compilers reach for one.

The idea in one sentence

A state machine is a piece of code that remembers where it is across multiple calls — an explicit state variable, plus a single entry point (e.g., MoveNext()) that branches on that state to do the next chunk of work and then returns.

A tiny example: iterators (yield return)

You've already used a compiler-built state machine if you've ever written yield return. This source:

IEnumerable<int> Count()
{
    yield return 1;
    yield return 2;
    yield return 3;
}

...is lowered by the C# compiler into something like:

class <Count>d__0 : IEnumerator<int>
{
    int state;       // where am I?
    int Current;     // what's the value right now?

    bool MoveNext()
    {
        switch (state)
        {
            case 0: Current = 1; state = 1; return true;
            case 1: Current = 2; state = 2; return true;
            case 2: Current = 3; state = 3; return true;
            default:               return false;
        }
    }
}

Each call to MoveNext() picks up where the previous one left off, produces the next value, advances state, and returns. The "execution" of the original method is now spread across many short calls into the same object.

Why compilers love state machines

  • Suspension and resumption. Code that "pauses" and resumes later (iterators, async, generators in other languages) can't fit on a normal call stack — the stack frame would be destroyed on return. A state machine moves that frame onto the heap as fields of an object.
  • Linear source, non-linear execution. You write a straight method body. The compiler chops it at the suspension points, numbers the chunks, and turns the body into a switch(state).
  • Local variables become fields. Any local that needs to survive a suspension is "lifted" to a field on the state machine object, so it persists between MoveNext() calls.

From iterators to async

async/await uses the same trick, with two twists:

  1. The "suspension trigger" is an awaitable that isn't done yet (a Task still in flight) instead of yield return.
  2. Resumption is driven by a callback — when the awaited operation completes, it calls MoveNext() again on the same state machine.
Key intuition: "async method" really means "method whose execution is sliced into pieces at await points, with a state machine stitching the pieces back together over time." The only open question is who builds and runs that state machine — the compiler (today) or the runtime (.NET 11).

With that mental model in place, the next sections look at the specific state machine Roslyn emits for an async method today, and what changes when the runtime takes over.

2. Compiler & runtime pipeline: how source becomes machine code

To understand what changes in .NET 11, it helps to see the full path source code takes. Every mainstream compiler — including Roslyn — runs the same conceptual stages, even when the boundaries blur.

The pipeline at a glance

What each stage actually does

  • Lexer (tokenizer): chops the raw source text into atomic tokens — keywords, identifiers, punctuation, literals. No knowledge of meaning.
  • Parser → AST (abstract syntax tree): turns the linear token stream into a tree that mirrors the grammar — MethodDeclaration contains a Block containing an AwaitExpression etc.
  • Semantic analysis: walks the AST and binds names to symbols (which ReadAsync? defined where?), infers types, runs type checking, evaluates overload resolution, applies attribute rules. Output is a bound tree — the AST plus a symbol table.
  • Lowering → IR: the compiler desugars high-level constructs into simpler primitives. This is where async/await, yield, foreach, using, pattern matching, and LINQ query syntax all get rewritten into method calls, loops, and (for async/iterators) explicit state machines. In .NET, the IR is CIL/IL (Common Intermediate Language). In LLVM-based toolchains it would be LLVM IR.
  • Assembly: IL plus type metadata is serialized into a portable file (.dll or .exe). This is what NuGet ships.
  • JIT (Just-In-Time) compiler: at runtime, the first time a method is called, the CLR reads its IL and emits native machine code for the current CPU/OS into executable memory. Subsequent calls jump straight to that native code.
  • CPU executes machine code: the literal bytes the JIT wrote (e.g., 48 8B 4C 24 20 = mov rcx, [rsp+20h] on x64) flow through the decoder, pipeline, branch predictor, and caches.

Interpreter vs compiler — a quick aside

The diagram's lower band shows the alternatives. An interpreter stops the pipeline early — either walking the AST directly (slow but simple, like a calculator) or interpreting a custom bytecode (CPython, classic JavaScript engines). A JIT mixes the two: interpret hot code only long enough to discover what to specialize, then compile that to native. A pure AOT compiler (Go, Rust, .NET NativeAOT) does all the back-end work before the program ever runs — no JIT at runtime, no IL files, just a native binary.

Two terms that show up in the rest of the doc

JIT intrinsic. An intrinsic is a method (or operator) whose name and shape the JIT recognizes specially — instead of emitting a normal call to the method body, the JIT substitutes a hand-tuned native code sequence. Familiar examples in .NET: Unsafe.As<T,U> (becomes a no-op cast), Sse2.Add (becomes a single paddd instruction), Math.Abs on a hot path (often a sign-bit mask, no call). For runtime async, calls like RuntimeHelpers.Await(task) are intrinsics: the JIT sees them in the IL and, rather than calling a method, splits the surrounding code at that point and weaves in suspension/resumption plumbing. Intrinsics let the runtime team add capabilities (like async suspension) without changing the C# language or the IL spec.
Liveness analysis. A standard dataflow analysis: for each program point, determine which local variables hold values that will be read again before being overwritten. A variable is "live" at point P if there's a path from P to a later read with no intervening write. The JIT uses this constantly — for register allocation (only live values need a register), for dead-code elimination (assignments to never-read locals can be deleted), and now for runtime async (only locals live across an await point need to be captured into the continuation). Classic compiler async pays for all locals that might be live (the lifted-field shape baked at compile time); runtime async pays only for the ones that actually are live at this specific await — usually a much smaller set.

The shift from compile-time to runtime-time state machine isn’t a wholesale rewrite of the toolchain — it’s a redistribution of work between stage (5) and stage (6). The IL gets simpler; the JIT gets smarter; the machine code at the bottom gets tighter on the hot path because the JIT can use facts (like "this Task already completed synchronously") that Roslyn couldn’t know at build time.

3. The starting point: a trivial async method

Imagine this innocent piece of code we'd write today:

public async Task<int> GetUserCountAsync(string tenant)
{
    var raw  = await _store.ReadAsync(tenant);
    var rows = await _parser.ParseAsync(raw);
    return rows.Count;
}

It looks sequential. What the compiler — and runtime — do with it is very different in the two worlds.

Today Compiler-generated state machine

Roslyn rewrites the method into a struct (or class on Debug) implementing IAsyncStateMachine. The method body becomes a giant switch on a state field driven by MoveNext().

.NET 11 Runtime async

The method body stays the method body. The runtime (JIT + VM) knows how to suspend and resume it at await points by capturing the necessary frame state directly.

4. What the compiler emits today

Conceptually, after Roslyn lowering, our 3-line method becomes something like this (simplified, but accurate in shape):

// 1. The outer "stub" replaces the body you wrote.
public Task<int> GetUserCountAsync(string tenant)
{
    var sm = new <GetUserCountAsync>d__7();
    sm.<>t__builder = AsyncTaskMethodBuilder<int>.Create();
    sm.<>4__this   = this;
    sm.tenant      = tenant;
    sm.<>1__state  = -1;
    sm.<>t__builder.Start(ref sm);  // calls MoveNext() the first time
    return sm.<>t__builder.Task;
}

// 2. The state machine itself.
[CompilerGenerated]

{
    public int <>1__state;
    public AsyncTaskMethodBuilder<int> <>t__builder;
    public MyService <>4__this;
    public string tenant;

    private string <raw>5__1;
    private List<Row> <rows>5__2;

    // Awaiter slots, one per distinct await:
    private TaskAwaiter<string>        <>u__1;
    private TaskAwaiter<List<Row>>  <>u__2;

    void IAsyncStateMachine.MoveNext()
    {
        int state = <>1__state;
        int result;
        try
        {
            TaskAwaiter<string> aw1;
            TaskAwaiter<List<Row>> aw2;
            switch (state)
            {
                default:
                    aw1 = <>4__this._store.ReadAsync(tenant).GetAwaiter();

                    {
                        <>1__state = 0;
                        <>u__1     = aw1;
                        <>t__builder.AwaitUnsafeOnCompleted(ref aw1, ref this);
                        return;       // suspend

                    goto resume1;

                case 0:
                    aw1 = <>u__1;
                    <>u__1 = default;
                    <>1__state = -1;
                    resume1:
                    <raw>5__1 = aw1.GetResult();

                    aw2 = <>4__this._parser.ParseAsync(<raw>5__1).GetAwaiter();

                    {
                        <>1__state = 1;
                        <>u__2     = aw2;
                        <>t__builder.AwaitUnsafeOnCompleted(ref aw2, ref this);
                        return;       // suspend
                    }
                    goto resume2;

                case 1:
                    aw2 = <>u__2;
                    <>u__2 = default;
                    <>1__state = -1;
                    resume2:
                    <rows>5__2 = aw2.GetResult();

                    result = <rows>5__2.Count;
                    break;
            }

        catch (Exception ex)

            <>1__state = -2;
            <>t__builder.SetException(ex);
            return;
        }
        <>1__state = -2;
        <>t__builder.SetResult(result);

}

What this costs us

  • Allocations on first suspension: the struct gets boxed onto the heap, the Task<int> is allocated, and the MoveNextRunner delegate is created. Cold-path-with-occasional-await methods pay this every time they actually suspend.
  • Lifted locals: every local that crosses an await becomes a field on the heap-allocated state machine — including large structs, which can balloon the box.
  • Stack noise: in profilers and exceptions you see MoveNext frames and AsyncMethodBuilderCore.Start instead of your real call chain.
  • Two-method shape: the stub + the MoveNext can't be inlined and the JIT has to treat them as separate units.

5. What the runtime does in .NET 11

With DOTNET_RuntimeAsync=1, Roslyn emits a much simpler signature, and the JIT does the suspension plumbing. Conceptually the IL looks like:

// Marked with a new flag in metadata: this method is "runtime-async".
[RuntimeAsyncMethod]
public Task<int> GetUserCountAsync(string tenant)
{
    // The body is essentially the source as written.
    string      raw  = RuntimeHelpers.Await(_store.ReadAsync(tenant));
    List<Row> rows = RuntimeHelpers.Await(_parser.ParseAsync(raw));
    return RuntimeHelpers.AsyncReturn(rows.Count);
}

The RuntimeHelpers.Await call is a JIT intrinsic. When the JIT compiles the method, at each await point it knows how to:

  1. Check if the awaited operation already completed (fast path: continue inline, no allocations).
  2. If not, capture only the live state at this exact point (think: the values of locals that are actually used after the await — the JIT does liveness analysis).
  3. Park that captured state somewhere efficient (often a small heap object sized to the live set, not to all locals).
  4. Return a Task to the caller.
  5. On completion, jump back to the resume point with the captured locals restored.
Key idea: the state machine still exists conceptually, but it's now an internal runtime detail — sized by JIT liveness analysis rather than a struct shape baked at compile time. That's where most of the wins come from.

7. Side-by-side: what changes in practice

AspectCompiler state machine (today)Runtime async (.NET 11)
Allocation on suspension Box of full state machine + Task + delegate Single object sized to JIT-live locals; pooled where possible
Allocation on sync completion None (if all awaits hit IsCompleted), but ValueTask still needed to avoid Task alloc None — the JIT recognizes the fully-sync path and never builds heap state
Stack traces in exceptions MoveNext frames + "--- End of stack trace from previous location ---" stitches Logical async stack reconstructed by the runtime; reads like sync code
Profiler stacks (PerfView, dotnet-trace) Noisy: AsyncTaskMethodBuilder.Start → MoveNext → user code Clean: user frame directly; suspensions visible as a distinct event
Locals across awaits Every "maybe-live" local is lifted to a field Only locals actually live at the await point are captured
Inlining Stub and MoveNext are separate methods; very limited inlining JIT can inline across awaits when the awaited result is known sync
Debugger step-through Step Over an await often lands in framework code Step semantics map closer to source order; resume is a single logical step
AsyncLocal<T> propagation Via ExecutionContext copy-on-write; caller never sees callee’s writes Writes propagate along the logical async call (more thread-local-like); see callout below
The AsyncLocal change is the big behavioral footgun. Today, if a callee sets AsyncLocal<T>.Value = x, the caller will not observe that change after the call returns — ExecutionContext is copy-on-write. In runtime async, the propagation model lets those writes flow back along the logical call. Code that depends on the old "isolation" behavior (e.g., scoped overrides via using var _ = new AsyncLocalScope(...)) needs to be audited before flipping the switch.

8. Why this matters for our sync major service

  • Today we’re mostly sync. Immediate wins are small — we don’t pay the state-machine tax on code we never made async.
  • The future cost of going async drops sharply. One reason hot paths stay sync is the allocation/stack tax on rare-suspension paths. Runtime async makes "occasional await" close to free.
  • Diagnostics get better. When we do hit issues in async paths (e.g., I/O, retries), cleaner profiler stacks and coherent exception traces save real time during livesite.
  • Watch for tooling lag — APM agents. "APM agents" are Application Performance Monitoring agents: in-process libraries (Application Insights / OpenTelemetry .NET / Dynatrace / AppDynamics / New Relic, etc.) that hook into the CLR via the ICorProfiler profiling API, System.Diagnostics.DiagnosticSource, or EventPipe to capture spans, dependency calls, exceptions, and metrics. They typically rewrite IL or attach to method-enter/exit events to time async operations — including walking the <...>d__N state-machine struct to follow continuations. With runtime async, that struct doesn't exist as the agent expects, and method-enter/leave timing doesn't map cleanly to suspension. Until each vendor ships a runtime-async-aware build, traces from runtime-async code can show missing spans, mis-correlated parent/child relationships, or zero-duration outer operations.
  • Mixed-mode and "thunk overhead at the boundary." Mixed-mode means: some assemblies in the process compiled against the new runtime-async ABI (the JIT-managed shape), others still using classic Roslyn state machines. When a classic-async caller awaits a runtime-async callee (or vice versa), the runtime can't pass continuations directly — the two sides expect different calling conventions for suspension/resumption. The CLR inserts a small auto-generated stub at the boundary — a thunk — that adapts between the two. A thunk is just a tiny piece of generated machine code: "translate the args/return shape, possibly allocate a classic-style Task wrapper, invoke the other side, and translate the result back on the way out." Each crossing is fast (a handful of instructions plus possibly one allocation for the wrapper Task), but in a hot loop that does many crossings (e.g., a sync-major-service path calling into a classic-async logger or telemetry library on every request), those costs add up. The pragmatic answer is to enable runtime async process-wide once your full dependency closure supports it, so boundary thunks vanish.

9. How to try it

# Per-process opt-in:
$env:DOTNET_RuntimeAsync = "1"
dotnet run -c Release

# Or via runtimeconfig.template.json:
{
  "configProperties": {
    "System.Runtime.Async.Enabled": true
  }
}

Good first experiment: take one of our async-ish helpers, enable the flag, capture an allocation profile with dotnet-counters + dotnet-trace, and diff against the baseline. Then deliberately throw an exception across two awaits and compare the stack traces.
