1. Why this lab exists — the long-haul replication story

A real-world ticket: a service replicating between two distant regions (a US ↔ APAC pair, roughly 180 ms RTT) was running slow. The investigation concluded:

"The issue is indeed due to sender-side socket size not being big enough, even though TCP window scaling is working well."

That sentence packs in a lot: - "Sender-side socket size" — the sender's send buffer (SO_SNDBUF). - "TCP window scaling working well" — the RFC 7323 option negotiated correctly during the SYN. - "Not big enough" — smaller than the BDP of the US↔APAC path.

This lab exists to see all of that on the wire, so I can recognize it next time without anyone hand-holding me through the diagnosis.

2. The networking layer cake

Every packet you ever send is a stack of envelopes:

│ L2  Ethernet frame (MAC + payload + CRC) │
│  ┌────────────────────────────────────┐  │
│  │ L3  IPv4 header (20B) + payload    │  │
│  │  ┌──────────────────────────────┐  │  │
│  │  │ L4  TCP header (20B) + data  │  │  │
│  │  │  ┌────────────────────────┐  │  │  │
│  │  │  │ L7  HTTP / TLS / etc.  │  │  │  │
│  │  │  └────────────────────────┘  │  │  │
│  │  └──────────────────────────────┘  │  │
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
Layer Adds Concerned with
L2 Ethernet 14 B header + 4 B CRC Reaching the next hop on a wire
L3 IP 20 B header Reaching any host on the planet (routing)
L4 TCP 20 B header (+ options) Reliable, ordered, flow-controlled stream

Every concept below is one of these layers' rules being enforced.

3. MTU — Maximum Transmission Unit

MTU = biggest single packet (frame) a link can carry without chopping it up. Measured in bytes, set per interface.

Common values

Link MTU
Ethernet (default) 1500
Wi-Fi 1500
PPPoE (DSL) 1492
Cloud overlay (VXLAN) 1450
VPN (IPSec/WireGuard) ~1400
IPv6 minimum 1280
Loopback 65535
Jumbo frames (intra-DC) 9000

MTU vs MSS

MTU  = 1500   (Ethernet frame payload)
      − 20    (IP header)
      − 20    (TCP header)
      ──────
MSS  = 1460   (actual TCP data per packet)

MTU is the truck size (L2). MSS is the cargo space (L4).

Truck analogy 🚛

  • MTU = the truck's height limit on a given road.
  • Cargo bigger than the truck → must split across multiple trucks (fragmentation) OR be dropped.
  • The whole journey is capped by the smallest truck along the route → Path MTU.

Jumbo frames (MTU 9000)

A jumbo frame is any Ethernet frame larger than the standard 1500-byte MTU — almost always 9000 bytes in practice. It's an optional Ethernet feature: not in the original spec, not universally supported, but ubiquitous inside modern datacenters.

Why anyone wants them

Headers don't get bigger when payloads do. So bigger payloads = a much smaller percentage of every byte is overhead.

Metric MTU 1500 MTU 9000 Improvement
TCP+IP+Eth header bytes 54 54 —
Useful payload per frame 1446 8946 6.2×
Header overhead 3.6% 0.6% 6× less waste
Packets to send 1 MB ~727 ~117 6.2× fewer
Interrupts / DMA setups per MB 727 117 6× less CPU
Context switches High Low Substantial

For high-throughput workloads (storage replication, backup, VM live-migration, MPI/HPC), CPU is often the bottleneck before bandwidth — fewer-but-bigger packets free up cycles for the actual application.

When they help

✅ Within a single rack or datacenter. ✅ End-to-end path entirely under your control (every switch, NIC, and host configured for 9000). ✅ Storage-style workloads (iSCSI, SMB Direct, replication).

When they hurt

❌ One device in the path stuck at 1500 → ICMP "needs fragmentation" storm, or silent black hole. ❌ Cross-region / public internet — the path almost certainly includes 1500-byte hops. ❌ Mixed environments where some VMs/containers are configured differently.

The gotcha

Jumbo is all-or-nothing along the path. Every hop must agree: NIC ↔ switch ↔ switch ↔ NIC. A single 1500-byte link in the middle and you're worse off than plain Ethernet — either fragments, drops, or hangs.

Likely relevance to your service

  • Within a DC (intra-DC replication between service replicas) → jumbo plausible.
  • Cross-region (US ↔ APAC) → almost certainly not jumbo. The public/long-haul fabric is 1500 (or smaller after VXLAN/IPSec encapsulation). That's why MSS values we'd see on the wire would be ~1380–1460, not ~8960.

How to spot it in Wireshark

Look at frame length (frame.len) on a sustained transfer. Capped at ~1514 → standard Ethernet. Frames in the 9000–9018 range → jumbo. The MSS in the SYN reveals the receiver's claim before any data flows.

🧒 Analogy: A regular truck holds 1.5 tons. A jumbo truck holds 9 tons. Both have one driver, same paperwork, one fuel stop. If every road on the route accepts jumbo trucks, you move stuff with 6× less driver time. But if any one road has a 1.5-ton bridge, jumbo trucks have to dump cargo and split, or just turn around — and now you're worse off than if you'd used regular trucks the whole way.

TL;DR: Jumbo frames trade compatibility for efficiency. Datacenters love them, the internet won't tolerate them.

Fragmentation — a numerical walkthrough 🔍

Here's exactly what happens when a too-big packet meets a smaller-MTU link with DF = 0 (fragmentation allowed). We'll trace the bytes.

Setup

  • App writes 3,980 bytes of payload.
  • Becomes one IP packet: 20 B IP header + 3,980 B data = 4,000 B total.
  • Identification field (chosen by sender, random per-packet): 0xABCD.
  • Next-hop link MTU is 1,500 B.
  • Router must fragment.

Constraints the router obeys

  1. Each fragment ≤ MTU (1,500 B).
  2. Each fragment has its own 20 B IP header (so payload per fragment ≤ 1,480 B).
  3. Fragment payload size must be a multiple of 8 bytes (because the fragment offset field counts in 8-byte units).
  4. All fragments share the same Identification value (so the receiver knows which pieces belong together).
  5. More Fragments (MF) = 1 on all but the last; MF = 0 on the last.
  6. Fragment Offset = where this fragment's payload starts in the original packet, ÷ 8.

How the router splits 3,980 bytes of payload

Largest payload chunk that fits and is a multiple of 8 → 1,480 B (since 1500 − 20 = 1480, and 1480 / 8 = 185 ✅).

# IP header Payload bytes Total size Identification MF flag Offset (8-byte units) Offset (bytes)
Fragment 1 20 B 1,480 B (bytes 0–1,479) 1,500 B 0xABCD 1 0 0
Fragment 2 20 B 1,480 B (bytes 1,480–2,959) 1,500 B 0xABCD 1 185 1,480
Fragment 3 20 B 1,020 B (bytes 2,960–3,979) 1,040 B 0xABCD 0 370 2,960
Sum 60 B headers 3,980 B payload 4,040 B on wire — — — —

Notice: original was 4,000 bytes. After fragmenting, we put 4,040 bytes on the wire (3 IP headers × 20 B = 60 B, minus the 20 B header we'd have used anyway = +40 B overhead). Fragmentation costs ~1% in raw bytes here — but vastly more in CPU and reliability.

Reassembly at the destination

  1. OS keeps a buffer keyed by (source IP, dest IP, protocol, Identification).
  2. As each fragment arrives, OS places its bytes at offset × 8 in the buffer.
  3. When MF=0 fragment arrives, OS knows the total length.
  4. When all bytes 0..length-1 are filled, the original packet is delivered up the stack.
  5. Timer: if not all fragments arrive within ~30 seconds (or 60 s on Linux), the buffer is dropped — entire packet lost, must be retransmitted by TCP.

Why fragmentation is so painful

  • Lose any one fragment → the whole packet is dropped → TCP retransmits all 4,000 bytes → router fragments again → vulnerable again.
  • Firewalls/IDS often drop fragments outright (they can't see TCP headers in fragments 2 and 3, since only fragment 1 has them — security risk).
  • Routers can't fragment in hardware fast paths — kicks to slow CPU paths.
  • Reassembly attacks (overlapping fragments, tiny fragments) are classic exploits.

That's why modern stacks set DF=1 and rely on PMTUD to discover the right size up front, then send only properly-sized packets.

Tying MTU together

  • MTU = the truck's height limit on one road segment.
  • Path MTU = the smallest truck limit along the whole route.
  • PMTUD = the process of discovering path MTU via ICMP feedback.
  • MSS = the cargo size TCP picks (= MTU − headers) based on what the peer advertised.
  • Fragmentation = the "fallback" when something didn't get the memo.

4. Tunnels and their MTU cost

Each tunnel wraps your packet in another envelope. Every wrapper steals bytes from your usable payload.

┌─ Outer envelope (transport) ────────────────┐
│  ┌─ Tunnel header (PPP/IPSec/VXLAN/…) ────┐ │
│  │  ┌─ YOUR ACTUAL IP+TCP+DATA ─────────┐ │ │
│  │  └────────────────────────────────────┘ │ │
│  └────────────────────────────────────────┘ │
└─────────────────────────────────────────────┘

4.1 PPPoE — Point-to-Point Protocol over Ethernet

  • Where: residential DSL / fiber-to-the-home.
  • Why: ISP authentication (username/password) + dynamic IP assignment.
  • Overhead: 8 B (2 B PPP + 6 B PPPoE) → MTU 1492.
  • 🧒 Your house's mail goes into a special ISP envelope labeled with your account number.

4.2 IPSec — Internet Protocol Security

  • Where: corporate VPNs, Azure VPN Gateway, AWS VPN, Cisco AnyConnect.
  • What: encrypts + authenticates IP packets.
  • Modes: transport (host-host) and tunnel (network-network, common).
  • Overhead: ~50–73 B → MTU ~1438–1400.
  • 🧒 Letter inside a locked steel box inside a normal envelope.
  • 🪤 Classic symptom: VPN connects, ping works, big pages hang → MTU + broken PMTUD.

4.3 WireGuard

  • Where: Tailscale, Mullvad, modern self-hosted VPNs.
  • What: IPSec's modern simpler cousin (~4,000 lines of code, fixed ChaCha20+Poly1305+Curve25519 crypto).
  • Overhead: 60 B → MTU 1440.
  • 🧒 Same locked-box idea, but the box is sleeker and there's only one model.

4.4 VXLAN — Virtual Extensible LAN

  • Where: cloud datacenters (Azure VNet, AWS VPC, Kubernetes CNI like Calico/Flannel, VMware NSX).
  • What: wraps Ethernet frames inside UDP packets so VMs on different physical hosts pretend to share a LAN.
  • Why: 24-bit network ID (~16M tenants) vs classic VLAN's 12 bits (~4K), and spans routers.
  • Overhead: 50 B (20 IP + 8 UDP + 8 VXLAN + 14 inner Ethernet) → MTU 1450.
  • 🧒 Apartment-internal mail wrapped in a citywide UDP envelope; receiving building unwraps it.

4.5 GRE — Generic Routing Encapsulation

  • Where: older site-to-site tunnels, Cisco networks, Azure ExpressRoute private peering, CDN / anti-DDoS providers (Cloudflare, Akamai, Imperva Magic Transit).
  • What: generic wrapper for any L3 protocol inside IP. No encryption.
  • Overhead: ~24 B → MTU ~1476.
  • Often stacked GRE + IPSec = generic tunneling + multicast + encryption (smaller MTU still).
  • 🧒 Plain box with a customs declaration. Doesn't lock; just says "deliver this."

Why GRE "provides multicast support" 📡

Multicast is a way of sending one packet to many receivers at the IP layer (vs unicast 1-to-1 or broadcast 1-to-all). Special address range 224.0.0.0/4. Used by: - Routing protocols (OSPF uses 224.0.0.5, EIGRP uses 224.0.0.10) - IPTV / video streaming inside a provider's network - mDNS / Bonjour service discovery on a LAN - Stock-ticker feeds, financial market data - Service-discovery in datacenters

IPSec in transport mode cannot carry multicast natively (the security associations are unicast). So if you need to send routing protocol updates or multicast traffic across an encrypted tunnel, the canonical fix is:

   Original multicast packet (e.g., OSPF hello to 224.0.0.5)
        │
        └─► Wrap in GRE        ← GRE doesn't care about the L3 payload
                │                  (multicast, IPv6, IPX, whatever)
                └─► Wrap in IPSec  ← Now the GRE-wrapped multicast looks
                       │              like a normal unicast IPSec packet
                       └─► Send across the public internet

That's the GRE-over-IPSec pattern. The phrase "GRE provides the tunneling and multicast support" means: GRE is the layer that carries the multicast packet from one site to another; IPSec is the layer that encrypts the resulting tunneled traffic.

Why CDN / anti-DDoS providers use GRE

Imagine you're under attack. You point your DNS at Cloudflare instead of your origin. Cloudflare's network absorbs the attack, filters the traffic, and forwards the clean part back to your origin server through a GRE tunnel. Your real origin IP stays hidden; only Cloudflare's IPs are publicly known.

Internet  ──▶  Cloudflare edge  ──GRE tunnel──▶  your origin server
(attackers and    (filters,                       (sees clean
 legit users)     terminates TLS)                  traffic only)

Same pattern: Akamai Prolexic, Imperva Magic Transit, Azure DDoS Protection's BGP-routed mitigation. GRE is the standard "scrubbing return path."

Azure ExpressRoute private peering

ExpressRoute is a dedicated private fiber connection from your on-premises datacenter into Azure, bypassing the public internet. Three "peering types":

Peering What you reach over it
Microsoft O365, Dynamics, Microsoft's PaaS public endpoints
Private Your own Azure VNet — as if it were an extension of your datacenter
Public (deprecated) (legacy public Azure services)

Private peering is what enterprise customers use to make Azure VMs look like local servers. It often layers GRE or other tunneling under the hood for L3 reach across the carrier's backbone.

4.6 Stacked tunnels

K8s pod traffic over corp VPN over home DSL:

  Original packet                            1500
    └─ VXLAN encap (pod overlay)             1450
        └─ IPSec encrypt (corp VPN)          1400
            └─ PPPoE (home ISP)              1392
                └─ Real Ethernet wire        1500 ✅ fits

Each layer only knows its own. The original app sees MTU 1500 and doesn't know about the 100+ bytes of headers ahead. Diagnosing requires peeling layers and probing with ping -f -l <size>.

Tunnel cheat sheet

Tunnel Purpose Encrypted? Overhead MTU
PPPoE ISP auth over DSL ❌ 8 B 1492
IPSec Encrypted VPN ✅ ~50–73 B ~1438
WireGuard Modern encrypted VPN ✅ 60 B 1440
VXLAN Multi-tenant L2-over-L3 ❌ 50 B 1450
GRE Generic L3-in-IP ❌ 24 B 1476

5. The DF bit and Path MTU Discovery

A 1-bit flag in the IPv4 header: "may routers fragment me if I'm too big?"

 0   1   2
┌───┬───┬───┐
│ 0 │DF │MF │
└───┴───┴───┘
   │   │   └─ More Fragments (1 = more pieces coming)
   │   └───── Don't Fragment (1 = forbidden to fragment)
   └───────── Reserved (always 0)

DF = 0 (clear) — fragmentation allowed

  • Router splits oversized packets, receiver reassembles.
  • ❌ Slow, fragile, lose-one-lose-all retransmits, firewalls drop fragments, hardware fast-path can't fragment.
  • The original IPv4 design. Modern networks avoid it.

DF = 1 (set) — fragmentation forbidden

  • Router drops oversized packets and sends back ICMP type 3 code 4: "Fragmentation Needed, MTU = N."
  • Sender shrinks future packets to fit. This is Path MTU Discovery (PMTUD).
  • ✅ Fast, predictable. Modern TCP default everywhere.

The PMTU Black Hole 🕳️

If a firewall blocks the ICMP reply, the sender never learns the path MTU. Symptoms: - ✅ Small ping works - ✅ TCP handshake works - ❌ Big transfers hang forever - ❌ HTTPS connects but pages never finish loading

Fix: unblock ICMP type 3 code 4, or use MSS clamping at the router (rewrite the TCP MSS option during the handshake so packets stay small from the start).

Probing path MTU yourself

# DF=1, payload 1472 → total 1500 → OK on Ethernet
ping -f -l 1472 8.8.8.8

# DF=1, payload 1473 → total 1501 → fails with "needs fragmentation"
ping -f -l 1473 8.8.8.8

Path MTU = largest size that succeeds + 28 (IP 20 + ICMP 8).

6. TCP — the conversation layer

6.1 The 3-way handshake

Client                                Server
──┬──                                 ──┬──
  │── SYN  ────────────────────────▶   │   "Hi, here's my options"
  │  ◀──────────────────────── SYN/ACK │   "Hi back, here are mine"
  │── ACK  ────────────────────────▶   │   "Got it, let's go"
  │                                     │
  │── Application Data ───────────▶    │   (TLS handshake, then HTTPS)
  │  ◀───────────────────── More Data  │
  │── FIN  ────────────────────────▶   │   "I'm done"
  │  ◀──────────────────────── FIN/ACK │   "Same, bye"

The first ACK measures RTT. Both sides commit to the options exchanged in SYN and SYN/ACK for the lifetime of the connection.

6.2 SYN options: MSS, Window Scale, SACK, Timestamps

The SYN is a business card announcing capabilities. Key options:

MSS — Maximum Segment Size

  • "Biggest TCP payload you can send me without fragmenting."
  • Typical: 1460 on Ethernet (1500 MTU − 40 headers).
  • 🧒 "My mailbox slot is 1460 mm wide."

Window Scale (RFC 7323)

  • The TCP "window size" field is 16 bits → max 65,535 bytes. Too small for modern links.
  • Window Scale: 8 means multiply every window value I send by 2⁸ = 256. So "1000" really means 256,000 B.
  • Only negotiated in the SYN. If either side omits it, scaling is off for the whole connection.
  • 🧒 "When I say my cup is '10 big', I really mean 10 × 256 sips."
  • 🎯 This is the option the original ticket said "is working well".

SACK — Selective Acknowledgment

  • "If you drop packet 5 but I received 6, 7, 8 — I can tell you that, so you only resend 5."
  • Without SACK: lose one, retransmit everything after it (wasteful).
  • 🧒 "Brick #5 fell off the truck. Resend just #5, I've got the rest."

Timestamps

  • Per-packet timestamp pair (10 B) → accurate RTT measurement + PAWS (sequence-wrap protection on fast links).

A real SYN

TCP, Src: 53412, Dst: 443, Flags: SYN
  Window: 65535
  Options (28 bytes):
    Maximum Segment Size: 1460
    SACK Permitted
    Window Scale: 8 (multiplier 256)
    Timestamps: TSval 4294943, TSecr 0
    NOP padding

Connection-wide rules are decided in the first two packets. Get them wrong → handicap for the connection's life.

7. BDP — Bandwidth-Delay Product

The number of bytes that can be "in flight" at any instant to keep a link 100% busy.

BDP (bytes) = Bandwidth (bytes/sec) × RTT (sec)

Unit conversions to get right

  • Bandwidth is sold in bits/sec (lowercase b). Buffers are in bytes (uppercase B). ÷ 8.
  • RTT is reported in ms by ping. ÷ 1000 for seconds.

Examples

Path Bandwidth RTT BDP
Office LAN 1 Gbps 1 ms 125 KB
Same-region cloud 10 Gbps 1 ms 1.25 MB
US East ↔ US West 1 Gbps 70 ms 8.75 MB
US ↔ APAC 10 Gbps 180 ms 225 MB 🤯
Starlink 100 Mbps 50 ms 610 KB

The inverse — throughput from a window

Max throughput = Window size ÷ RTT

64 KB window across US↔APAC (180 ms):

65,536 B / 0.180 s ≈ 364 KB/s ≈ 2.85 Mbps

A 10 Gbps link, throttled to 2.85 Mbps by a 64 KB pitcher. That is the original ticket in one fraction.

Mental shortcuts

  • 1 Gbps: BDP in KB ≈ 125 × RTT(ms)
  • 10 Gbps: BDP in MB ≈ 1.25 × RTT(ms)

Intuition

RTT is how long until you get permission (the ACK) to send more. - Window = BDP → pipe perfectly full, max throughput. 🎯 - Window < BDP → pipe partially empty, capped at window/RTT. - Window > BDP → no extra benefit (link can't carry more).

8. Long Fat Networks and the "bravery to send" insight

Long Fat Network (LFN) — RFC 1323/7323

Pronounced "el-fen". A network where BDP > 64 KB — so big that the original 16-bit TCP window can't fill it.

Dimension Meaning
Long High RTT — geographic distance, satellite hops
Fat High bandwidth — 1/10/100 Gbps
  • LAN (1 Gbps, 1 ms) = fat but short ❌
  • Dial-up (56 kbps, 200 ms) = long but thin ❌
  • US↔APAC (10 Gbps, 180 ms) = long AND fat ✅

The insight

"On long fat networks, the bottleneck isn't bandwidth — it's how much data you're brave enough to send before getting an ack."

For short networks, slow = buy more bandwidth. For LFNs, you can have a dedicated empty 10 Gbps fiber and still get 2 Mbps — because TCP sends a tiny burst, waits 180 ms for the ACK, sends another tiny burst. More bandwidth changes nothing.

What helps: larger windows / buffers → more bytes in flight before waiting.

Why "brave"?

Sending unacked data is a risk: - If anything along the path drops it, it all has to be retransmitted. - TCP starts cautiously (slow start) — doubles its window per RTT. - The sender's OS caps in-flight bytes at SO_SNDBUF no matter what the receiver advertises. - Bravery = how much memory the sender is willing to commit and potentially lose.

Modern OSes auto-tune SO_SNDBUF up to ~16 MB. Some systems pin it static at 64 KB — that was the bug in the original case.

9. The chain of throughput caps

Actual throughput is the minimum of all of these:

throughput ≤ min(
    link_bandwidth,            ← physics (the wire itself)
    rwnd / RTT,                ← receiver's advertised window
    cwnd / RTT,                ← sender's congestion window (TCP self-regulation)
    SO_SNDBUF / RTT,           ← sender's socket buffer    ← original cap lived here
    SO_RCVBUF / RTT            ← receiver's socket buffer
)

To be link-bandwidth-bound (the good case), every other term must equal or exceed BDP.

How they differ

Cap Set by Adjusts?
rwnd Receiver app Per ACK, based on read rate
cwnd TCP sender algorithm Slow start, congestion avoidance, MD on loss
SO_SNDBUF Sender OS / app Static unless auto-tuning is on
SO_RCVBUF Receiver OS / app Static unless auto-tuning is on

The original ticket had: rwnd healthy ✅, cwnd healthy ✅, window scaling negotiated ✅ — but SO_SNDBUF was statically too small ❌.

10. Case study: cross-region replication latency

Symptom

Replication latency between two distant regions (a US ↔ APAC pair, ~180 ms RTT) was high. Livesite monitoring dashboards flagged the SLA breach.

What the team checked, in order

  1. Link health — both endpoints reachable, no packet loss → ✅
  2. MTU / PMTUD — ping -f -l <size> worked at expected sizes; no ICMP black hole → ✅
  3. TCP window scaling negotiated — captured SYN/SYN-ACK showed Window Scale: 8 on both sides → ✅
  4. Receiver-side window (rwnd) — receiver advertising hundreds of KB at scale → ✅
  5. Congestion window (cwnd) — no excessive retransmits or drops → ✅
  6. Sender-side socket buffer (SO_SNDBUF) — pinned static, smaller than the 225 MB BDP → ❌ this was it

The arithmetic

Link:           10 Gbps   = 1.25 GB/s
RTT:            180 ms    = 0.18 s
BDP:            225 MB
Sender buffer:  64 KB     (static)
Throughput cap: 65,536 / 0.180 ≈ 356 KB/s ≈ 2.85 Mbps
% of link used: 0.03 %

The fix

Increase SO_SNDBUF (or enable OS auto-tuning) on the sender to ≥ BDP for the path. Overnight throughput goes from 2.85 Mbps to multi-Gbps. Nothing physical changed — just a number in a kernel struct.

Why I wrote this whole doc

So that next time I see "window scaling working, throughput still bad", I can immediately think "sender buffer < BDP" without re-deriving everything from scratch.

12. PMTUD diagnostics — the engineer's checklist

Before blaming the sender buffer, every network engineer eliminates path MTU problems first. Here's the checklist, in order, with the actual commands.

Step 1 — Is the path MTU what we think it is?

# DF=1, payload size + 28 = total. Largest size that succeeds = path MTU − 28.
ping -f -l 1472 <target>          # 1472 + 28 = 1500 → expect OK on Ethernet
ping -f -l 1473 <target>          # 1473 + 28 = 1501 → expect "needs fragmentation"

# Binary search if 1472 fails — start lower
ping -f -l 1400 <target>
ping -f -l 1350 <target>

Interpretation: - 1472 succeeds, 1473 fails → path MTU 1500 ✅ (the normal case) - 1400 succeeds, 1500 fails without error message → PMTU black hole 🕳️ - All sizes fail → ICMP itself blocked, can't measure

Step 2 — Is PMTUD actually reaching us?

If a router along the path is dropping oversized packets, it should send back an ICMP type 3 code 4 ("Fragmentation Needed, DF Set") message containing the MTU it can handle.

Capture that:

tshark -i <iface> -f "icmp" -w icmp.pcapng
# In another shell, generate the failing traffic (e.g., big curl download)
# Stop capture, then:
tshark -r icmp.pcapng -Y "icmp.type == 3 and icmp.code == 4" -V

Look for fields: - Length of original datagram — what the router saw - MTU of next hop — what it wants you to use

If you see these → PMTUD is working. Sender will shrink, life continues. If you see no ICMP at all when probing with -f -l <large> → black hole.

Step 2.5 — Prove "ICMP itself isn't broken" 🩺

Before you trust any PMTUD result, prove the ICMP channel is alive end-to-end. A "no ICMP reply" only means something is broken — it could be the router, the path, or the firewall rules at either end. Here's the layered test ladder:

# Test Command What a pass looks like
1 ICMP Echo to nearby host ping <local-gateway> Reply in <5 ms
2 ICMP Echo to remote host ping <dest> Reply (any latency)
3 ICMP Echo with payload ping -l 1000 <dest> Reply, no truncation
4 ICMP "Time Exceeded" reachable tracert <dest> (Windows) / traceroute -I (Linux) Hops respond (not all * * *)
5 ICMP "Frag Needed" reachable ping -f -l 1472 <dest> then -l 1473 At threshold you see Packet needs to be fragmented but DF set.
6 Outbound ICMP allowed tshark -i <if> -f "icmp" while pinging Outgoing echo + incoming reply both visible
7 Inbound type 3 allowed tshark -i <if> -f "icmp[icmptype]==3" while transferring Any type-3 message at all 
# Composite one-liner: pin down what ICMP type/code is actually arriving
tshark -i 5 -f "icmp or icmp6" -T fields `
  -e frame.time_relative -e ip.src -e icmp.type -e icmp.code

Interpreting the matrix:

Result pattern Diagnosis
Echo works, type-3 never seen, big transfers stall Firewall blocks only the destination-unreachable subtype → classic PMTUD black hole
Echo fails entirely, traceroute also dead All ICMP blocked (corporate egress) → fix at the firewall, or use TCP-based PMTUD (RFC 4821)
Echo to gateway works, echo to dest fails ICMP blocked at peer/cloud edge → ask the other side
Echo intermittently fails, high loss NIC/cable/wireless issue — fix the L1/L2 layer first; PMTUD is the wrong rabbit hole
Echo OK but ping -f -l <huge> returns "Reply from … bytes=…" instead of "needs fragmentation" Some middlebox is silently fragmenting despite DF — PMTUD will appear to work but real flows still suffer

TCP-based PMTUD fallback (RFC 4821) — when ICMP truly cannot be fixed:

Modern Linux and Windows can probe path MTU using TCP segments themselves, no ICMP required. Enable:

# Windows: enable MTU black hole detection
netsh interface tcp set global pmtublackholedetect=enabled

# Linux: set per-route or globally
sysctl -w net.ipv4.tcp_mtu_probing=1   # 1 = on if ICMP black hole detected, 2 = always probe

This makes TCP itself binary-search the MTU by retransmitting smaller segments on suspected loss. It's slower than ICMP-driven PMTUD but survives hostile firewalls.

Step 3 — Is the sender being told (and reacting)?

# Watch the TCP MSS negotiated in your SYN
tshark -r capture.pcapng -Y "tcp.flags.syn==1" -T fields -e tcp.options.mss_val
# Compare to what the receiver sent

Linux can dump the cached PMTU:

ip route get <dest>     # shows mtu lock and current PMTU estimate

Windows shows it in the route table when PMTUD is on:

Get-NetIPInterface | Select-Object InterfaceAlias, NlMtu
netsh interface ipv4 show destinationcache

Step 4 — Suspect a black hole? Mitigate with MSS clamping

If ICMP is blocked but you control a router on the path (firewall, VPN gateway, load balancer), make it clamp MSS at TCP handshake time so the sender never tries packets bigger than the path can carry.

# Linux iptables example: clamp MSS to PMTU
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
         -j TCPMSS --clamp-mss-to-pmtu

Effect: TCP MSS option in SYN/SYN-ACK gets rewritten downward → sender sends only small enough segments from byte one → no need for PMTUD to work.

Step 5 — Only after Steps 1–4 clean, blame the sender buffer

By the time you reach this step: - ✅ Path MTU consistent and detected. - ✅ ICMP fragmentation messages reach us. - ✅ MSS in SYN is sane. - ✅ No reassembly errors in packet captures. - ❌ Throughput still bad.

Now run the chain-of-caps audit (Section 9). Likely culprit: SO_SNDBUF clamped statically, exactly the long-haul story.

13. Maximum protocol stacking — the worst-case packet

How many layers can a real-world packet have? Surprisingly many. Here's a plausible production stack from an Azure-hosted K8s workload that needs encrypted multicast across regions through a corporate VPN — basically every tunneling technology piled on at once.

The use case

Hypothetical: a healthcare company's HQ in NYC runs a Kubernetes cluster in Azure US-East. They replicate a multicast-based stock-price feed from their NYC datacenter into Azure pods. Traffic flows:

  1. NYC datacenter → multicast UDP feed
  2. → GRE tunnel to carry multicast over IP
  3. → IPSec ESP for encryption across the WAN
  4. → MPLS / ExpressRoute carrier transport
  5. → Azure VNet → VXLAN overlay between physical hosts
  6. → K8s pod network (another encapsulation in some CNIs)
  7. → finally, the TCP+TLS+HTTP/2 the app speaks

The layered stack on the wire

┌─ Ethernet header (14 B)                              ─┐
│  ┌─ Outer IPv4 header (20 B)                        ─┤
│  │  ┌─ UDP header (8 B)        ← VXLAN transport    ─┤
│  │  │  ┌─ VXLAN header (8 B)                        ─┤
│  │  │  │  ┌─ Inner Ethernet (14 B) ← bridged frame  ─┤
│  │  │  │  │  ┌─ IPv4 header (20 B)                  ─┤
│  │  │  │  │  │  ┌─ IPSec ESP header (~28 B + iv)   ─┤
│  │  │  │  │  │  │  ┌─ IPv4 header (20 B) inner     ─┤
│  │  │  │  │  │  │  │  ┌─ GRE header (4–8 B)        ─┤
│  │  │  │  │  │  │  │  │  ┌─ IPv4 header (20 B) original ─┤
│  │  │  │  │  │  │  │  │  │  ┌─ TCP header (20 B)        ─┤
│  │  │  │  │  │  │  │  │  │  │  ┌─ TLS record (5 B)       ─┤
│  │  │  │  │  │  │  │  │  │  │  │  ┌─ HTTP/2 frame (9 B)    │

│  │  │  │  │  │  │  │  │  │  │  │  │  │     payload...        │

Header budget arithmetic

Layer Header size
Ethernet 14 B
Outer IPv4 20 B
Outer UDP 8 B
VXLAN 8 B
Inner Ethernet 14 B
IPv4 (before IPSec) 20 B
IPSec ESP (header + IV + ICV + trailer) ~38 B
IPv4 (inner, post-IPSec) 20 B
GRE 4 B (min, 8 B with key/seq)
IPv4 (original packet) 20 B
TCP 20 B
TLS record header 5 B
HTTP/2 frame header 9 B
Total header overhead ~200 bytes

Effective MSS for the app

Starting from Ethernet 1500:

1500 (MTU)
−   8 (UDP-VXLAN-Eth = 30, but outer IP+UDP already 28, VXLAN 8, inner Eth 14 = 50)
... (do the full subtraction)

Worked from the outside in:

1500  Ethernet payload
−  20 outer IPv4
−   8 outer UDP
−   8 VXLAN
−  14 inner Ethernet
= 1450  available for the inner IP packet

1450
−  20 inner IPv4
−  38 IPSec ESP
= 1392  available for the IPSec-protected payload

1392
−  20 IPv4 (post-IPSec)
−   4 GRE
= 1368  available for the GRE-tunneled payload

1368
−  20 IPv4 (original)
−  20 TCP
= 1328  effective MSS for the app

1328
−   5 TLS record
−   9 HTTP/2 frame
=  1314 bytes per HTTP/2 frame ← the app gets THIS much per packet

Conclusion: the app believes it has 1460 bytes/segment, but on the wire, after stripping ~200 B of envelopes, only 1,314 useful bytes remain. ~12.4% of every packet is overhead rather than payload.

When this stack hurts

  • Throughput loss: 12% wasted directly.
  • CPU: each hop must encapsulate / decapsulate / encrypt / decrypt. At 10 Gbps, this can saturate cores.
  • MTU debugging nightmare: a 1500-byte misconfiguration anywhere along the path silently fragments at the outermost layer, and the inner application sees nothing useful.
  • PMTUD becomes a circus: the original TCP sender has no idea about VXLAN+IPSec+GRE in the middle. MSS clamping at every tunnel boundary is the only sane mitigation.

How to detect this in production

Tshark with frame.protocols shows the whole stack of dissectors for any frame:

tshark -r capture.pcapng -T fields -e frame.protocols -c 1
# Sample output:
# eth:ethertype:ip:udp:vxlan:eth:ethertype:ip:esp:ip:gre:ip:tcp:tls:http2

Each colon-separated token = one envelope. Reading that string tells you exactly what stack the packet traversed.

Bound: how deep can it go?

There's no hard protocol limit, but practical bounds: - Many switches/routers stop processing past ~7-8 levels of header parsing (offload engines give up). - Each layer eats ~10–40 bytes — past ~250 B of overhead, packets become uneconomic. - In practice the deepest production stacks are 4–6 layers; 8+ is research/lab territory.

The mental shortcut 🎯

Reading any packet is a chain of "what comes next?" questions. Each header's "next protocol" field is a pointer to the next decoder. Wireshark just walks this chain automatically. Tshark exposes the chain as frame.protocols.

Rule of thumb: if you see eth:ip:udp:vxlan:eth:ip:tcp in frame.protocols, you have a VXLAN tunnel. If you see eth:ip:esp:..., the inside is encrypted — without keys, that's where dissection stops. If you see eth:ip:gre:ip:tcp, GRE is doing the tunneling (no encryption).

15. FAQ — clarifications collected along the way

Q: What is wpcap.dll?

The packet-capture library Wireshark and tshark depend on to read raw frames off the NIC.

  • Originally part of WinPcap (Windows port of libpcap).
  • Today shipped by Npcap (WinPcap's modern successor); the file is kept named wpcap.dll for backward compatibility with apps written against the old API.
  • It's a userspace shim — the real kernel-level capture happens in npcap.sys.

"Userspace shim" — what does that actually mean? 🧩

Windows splits the world in two: - User mode (ring 3) — where your apps run. Crashes here just kill the app. No direct hardware access. - Kernel mode (ring 0) — where drivers live. Direct hardware access, but a crash blue-screens the whole machine.

To get raw packets, you must be in kernel mode (the NIC's DMA buffer is not exposed to user mode). But you don't want every app written in kernel C — that would be catastrophic for stability and security.

So Npcap splits the job in two: 1. npcap.sys lives in the kernel, hooks the NDIS stack, copies frames into a ring buffer. 2. wpcap.dll lives in user mode, exposes a friendly pcap_*() C API that apps link against. Internally each call (pcap_open_live, pcap_loop, pcap_compile) is translated into a DeviceIoControl() request sent down to the driver.

"Shim" = a thin translation layer that adapts one API to another with minimal logic of its own. - wpcap.dll doesn't do the capture; it's a thin wrapper around the kernel driver's IOCTL interface. - It also pretends to be the old WinPcap wpcap.dll for compatibility — that's another sense of "shim": a compatibility bridge so unmodified apps from the WinPcap era still work.

Analogies: - 🚪 wpcap.dll = doorman; npcap.sys = the room. Apps talk to the doorman, the doorman fetches what's inside. - 📞 wpcap.dll = receptionist that translates "I want packets from NIC 3 matching tcp port 443" into the kernel's internal IOCTL language. - 🔌 wpcap.dll = electrical adapter — you plug your foreign-spec appliance (an old WinPcap-era app) into it, and the wall socket (npcap.sys) doesn't care.

Without the shim, every app would need to: - Open \\.\NPCAP_xxx device handles directly - Speak raw IOCTL codes (BIOCSETF for BPF, BIOCGSTATS for stats…) - Re-implement BPF compilation

With the shim, an app just calls pcap_open_live("eth0", 65535, 1, 1000, errbuf) and the messy translation is somebody else's problem.

ASCII shorthand:

Wireshark / tshark   ─┐
nmap                  ├──▶  wpcap.dll  ─▶  npcap.sys  ─▶  NIC
custom tools         ─┘   (userspace API)  (kernel driver)

Full architecture diagram (SVG):

Read it top-down: apps call the pcap_*() API → wpcap.dll translates to IOCTLs → npcap.sys hooks the NDIS filter stack → frames are copied from the NIC's ring buffer into your capture file.

When tshark says "Unable to load Npcap (wpcap.dll)", the userspace doorway isn't there → Npcap isn't installed. When tshark finds wpcap.dll but lists only etwdump → wpcap loaded but npcap.sys isn't registered as an NDIS filter (incomplete install or service stopped).

Q: What does tshark -D do?

Lists every capture-able interface with an index number to pass to -i. Sample output:

1. \Device\NPF_{GUID}  (Wi-Fi)
2. \Device\NPF_{GUID}  (Ethernet)
3. \Device\NPF_{GUID}  (vEthernet (WSL))
4. \Device\NPF_Loopback (Adapter for loopback traffic capture)

Then tshark -i 2 -w mycapture.pcapng captures on interface 2. It's the first command in any tshark workflow — you need the index before anything else.

Q: If BDP isn't filled, does data fail to transmit?

No — data still transmits reliably; it just transmits slowly.

TCP always delivers your bytes correctly and in order. The window only affects speed.

Window ≥ BDP:
  [send send send send send send …]     ────▶ pipe full, max throughput
   ◀── ACKs streaming back continuously ──

Window < BDP:
  [send send send] ⏸️ wait... wait... ⏸️ [send send send] ⏸️
   tiny burst    │  waiting for ACK         next burst
                 ◀──────── 1 RTT ────────▶
   pipe sits half-empty between bursts

Worked example — 100 MB file across US ↔ APAC (10 Gbps, 180 ms RTT) with 64 KB buffer:

  1. Sender stuffs 64 KB into the pipe (~50 µs on 10 Gbps).
  2. Sender stops — outstanding-bytes limit hit.
  3. Sender waits 180 ms for the first ACK.
  4. ACK arrives → another 64 KB.
  5. Repeat.

Effective rate: ≈ 2.85 Mbps. The 100 MB file transfers in ~280 seconds instead of ~1 second on a saturated link. All bytes arrive. None are lost. It's just glacially slow.

What's actually true: | Claim | Verdict | |---|---| | Bytes don't get sent | ❌ False — all bytes delivered | | Bytes get dropped | ❌ False — TCP retransmits losses anyway | | Throughput caps at window / RTT | ✅ Yes | | Link bandwidth becomes irrelevant beyond this point | ✅ Yes | | App sees timeouts/errors | ⚠️ Only if the app has a deadline; TCP is content to trickle |

The real-world consequence isn't lost data — it's: - Replication-SLA breaches (deadline missed) - Backpressure: producer fills queues faster than slow pipe drains → OOM - Application-level retries (not TCP-level) → more connections on the same slow pipe - One slow connection blocking other work

That's why the long-haul symptom in dashboards was "replication lag growing", not "errors / loss".

30-second mental model ``` TCP guarantees: ✅ delivery, ✅ ordering, ✅ integrity TCP does NOT guarantee: ❌ speed

Window < BDP → trickle (still correct, just slow) Window ≥ BDP → flood (link-limited) Lost bytes → retransmitted automatically Slow bytes → too bad, that's between you, your buffer, and physics ```

Q: Example values for rwnd, cwnd, SO_SNDBUF?

All three are in bytes, but they're observed/set in different ways.

SO_SNDBUF / SO_RCVBUF — the static socket buffer ceiling. Set per socket by app or OS auto-tuning.

Scenario Typical value
Windows app, auto-tune on starts ~64 KB → grows to ~16 MB
Linux app, auto-tune on starts ~16 KB → grows to ~4 MB
setsockopt(SO_SNDBUF, 64*1024) called pinned at 64 KB ❌ — disables auto-tune
Tuned for cross-region replication 16–64 MB
100 Gbps research nets 256 MB+

🎯 The original culprit: explicit setsockopt to a small static value, killing auto-tune.

rwnd — receiver's advertised window. Visible in every ACK ("I have this much receive buffer free"). Changes packet-to-packet.

Receiver state rwnd
Empty buffer ~64 KB → grows with scaling
App reading fast high, close to SO_RCVBUF
App slow / sleeping shrinks as buffer fills
App stalled 0 → "zero window" → sender must pause

Wireshark shows Win=64512 [scaled: 16515072] — the raw 16-bit value × the scale factor.

cwnd — sender's congestion window. Invisible on the wire — purely a kernel variable on the sender.

State cwnd
Just connected (slow start) 10 × MSS ≈ 14.6 KB
After 1 RTT no loss doubles → ~29 KB
After 2 RTTs ~58 KB
... doubles each RTT until loss ...
On packet loss halves (multiplicative decrease)
Steady-state on clean network ≈ BDP

Observe on Linux: ss -tin shows cwnd:14 (in MSS units, × 1460 for bytes).

Worked example — 1 Gbps, 70 ms RTT (BDP = 8.75 MB):

After ~13 RTTs of clean slow start, cwnd reaches ~8.75 MB → matches BDP → throughput = 1 Gbps. ✅

Now pin SO_SNDBUF = 64 KB (the original bug):

Variable Value
cwnd grows to 8.75 MB (but no one cares)
rwnd grows to 16 MB (but no one cares)
SO_SNDBUF 64 KB ← the cap
Effective window min = 64 KB
Throughput 64 KB / 70 ms ≈ 7.5 Mbps on a 1 Gbps link

Healthy cwnd and rwnd cannot rescue you when SO_SNDBUF clamps the sender.

Q: What is DSL?

Digital Subscriber Line — internet over the same copper telephone wires that carry voice calls. 📞

The trick: voice uses 0–4 kHz; DSL uses the unused higher frequencies (25 kHz – 1+ MHz) on the same wire. A filter splits voice and data so you can be online and on a call simultaneously.

Tech Speed Notes
Dial-up (predecessor) 56 kbps Used voice band, tied up the line
ADSL 1–24 Mbps ↓ Common home broadband, 2000s–2010s
VDSL/VDSL2 50–100 Mbps Shorter range from exchange
G.fast ~1 Gbps Hybrid copper/fiber for last few hundred meters

DSL providers needed per-subscriber auth + dynamic IPs → wrapped PPP inside Ethernet → PPPoE → MTU drops from 1500 to 1492. That's why DSL users have famous MTU/VPN/CDN issues. DSL is being replaced by fiber and cable but still serves rural areas globally.

Q: What does "without flat Layer-2" mean?

A flat Layer-2 network = one giant broadcast domain spanning many hosts (and sometimes physical sites). Every host reaches every other host directly via MAC; every ARP/DHCP/broadcast hits everyone.

   Server A    Server B    Server C    ...   Server Z
      │           │           │              │
      └───────────┴── giant L2 broadcast ────┘
              (one VLAN, one failure domain)

Why it's bad at scale: - Broadcast storms (ARP, DHCP, misbehaving NICs flood everybody). - Failure domain too large — one misconfig takes down hundreds. - Spanning Tree Protocol gets brittle past a few hundred ports. - Hard/expensive to stretch across datacenters. - 12-bit VLAN tag → max ~4,094 networks. Clouds need millions.

VXLAN's gift: wraps L2 frames inside L3 UDP packets, so VMs feel like they share a LAN even across routed datacenter cores. You get L2 semantics (MAC reachability, broadcast within segment) on top of L3 scalability, no actual flat-L2 spanning required.

   L3 routed core (scalable, normal IP)
       â–²                  â–²
  ┌────┘                  └────┐
  │  VXLAN tunnel (L2-in-UDP)  │
 [VTEP]                       [VTEP]
   │ │                          │ │
  VM1 VM2 ← virtual LAN →     VM3 VM4

Rephrased: VXLAN gives apps the illusion of being on the same Ethernet LAN even when they're across routers and datacenters — without anyone actually deploying one giant Ethernet broadcast domain that spans those routers and datacenters.

Appendix A — Percentiles and tail latency

Came up while reading dashboards alongside the network investigation.

What a percentile is

Line up N samples sorted ascending. The Pₓ value is the one at position x % × N. - P50 = median (the typical experience) - P95 / P99 = the "bad-but-frequent" experience - P99.9 = the catastrophic edge that, at scale, hits everyone

Why mean lies — the canonical example

1,000 requests: - 990 × 10 ms = 9,900 ms - 10 × 5,000 ms = 50,000 ms - Mean = 59,900 / 1,000 ≈ 60 ms ✅ "fine" - P99 = 5,000 ms ❌ "10 users/sec are timing out"

The mean is a number nobody experienced. The P99 is a number someone definitely did.

Tail amplification (the killer at scale)

A request fanning out to 100 services, each with P99 = 1 s: - Prob all 100 return faster than P99: 0.99¹⁰⁰ ≈ 37% - 63% of users hit at least one tail call → see ~1 s. - A 1% service tail becomes a 63% user tail.

That's why Google/Amazon obsess over P99.9 and beyond.

Quick reference

Metric Tells you
Mean A blended number nobody experienced
P50 The typical experience
P95 / P99 The bad-but-frequent experience
P99.9+ The catastrophic edge (dominant at scale)
Max One-off worst case

"The average is the lie management wants to hear. The tail is the truth users live."
