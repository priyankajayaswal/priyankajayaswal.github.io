🗺️ Unified architecture — where every tool sits in the stack

This single picture maps every tool in this cheat sheet onto the Windows networking stack. Six vertical "pipes" by what API the tool uses; four horizontal layers from user app down to the wire. Use it to predict behavior: tools in the same column see the same data; tools in different columns can disagree (e.g., nslookup vs Resolve-DnsName, netsh vs Get-NetTCPSetting are alternates).

How to read it: - 🟦 blue = capture tools (read frames). 🟨 yellow = traffic generators / probes. 🟪 purple = state inspectors. 🟥 rose = configurators. - Tools in the same column share the same kernel doorway. That's why nslookup and Resolve-DnsName can return different answers (one bypasses the dnscache service), and why netsh and Get-NetTCPSetting are interchangeable (same params, two DLLs). - The two capture stacks (Npcap vs ETW) observe the same NDIS frames at different filter altitudes — that's why you can run pktmon and Wireshark on the same NIC simultaneously without conflict. - Everything ultimately funnels into one NDIS miniport feeding one physical NIC. The whole cheat-sheet is just different views of that single packet stream.

Wireshark / tshark

How it works (architecture)

Key takeaway: the GUI never touches the kernel — dumpcap is the only privileged piece. Extcap plugins give you the leftmost path without a kernel driver, which is why etwdump shows up even on a stock install with no Npcap.

Npcap stack zoom-in

Default install path on Windows: C:\Program Files\Wireshark\tshark.exe. PowerShell convenience:

Set-Alias tshark "C:\Program Files\Wireshark\tshark.exe"

List interfaces

tshark -D

Capture (live)

# Capture 60 seconds on interface 5, write pcapng
tshark -i 5 -a duration:60 -w capture.pcapng

# Capture only traffic to/from a host
tshark -i 5 -f "host example.com" -w example.pcapng

# Capture only HTTPS
tshark -i 5 -f "tcp port 443" -w https.pcapng

# Capture first 100 packets and stop
tshark -i 5 -c 100 -w sample.pcapng

# Ring buffer: 10 files × 50 MB each, rotate
tshark -i 5 -b filesize:51200 -b files:10 -w rolling.pcapng

Read (offline analysis)

# Dump packets with TCP details
tshark -r capture.pcapng -V | more

# One-line summary
tshark -r capture.pcapng

# Only TCP SYN packets, show options
tshark -r capture.pcapng -Y "tcp.flags.syn==1 and tcp.flags.ack==0" -V

# Show all ACK round-trip times
tshark -r capture.pcapng -T fields -e frame.time_relative -e tcp.analysis.ack_rtt -Y "tcp.analysis.ack_rtt"

# Show window-size advertisements per packet
tshark -r capture.pcapng -T fields -e frame.number -e tcp.window_size -e tcp.window_size_scalefactor

# Bytes in flight over time
tshark -r capture.pcapng -T fields -e frame.time_relative -e tcp.analysis.bytes_in_flight

# Show retransmissions only
tshark -r capture.pcapng -Y "tcp.analysis.retransmission"

# Show "TCP Window Full" events
tshark -r capture.pcapng -Y "tcp.analysis.window_full"

Statistics

# Conversation summary
tshark -r capture.pcapng -q -z conv,tcp

# IO graph (1-second bins)
tshark -r capture.pcapng -q -z io,stat,1

# Average ACK RTT per second
tshark -r capture.pcapng -q -z io,stat,1,"AVG(tcp.analysis.ack_rtt)tcp.analysis.ack_rtt"

# Expert info (retransmits, dup acks, window-full, zero-window)
tshark -r capture.pcapng -q -z expert

Useful display filters (-Y)

Filter What it shows
tcp.flags.syn==1 and tcp.flags.ack==0 Initial SYN only
tcp.flags.syn==1 and tcp.flags.ack==1 SYN/ACK only
tcp.analysis.retransmission Retransmits
tcp.analysis.window_full Sender is window-bound 🎯
tcp.analysis.zero_window Receiver said "stop sending"
tcp.analysis.duplicate_ack Receiver missing a segment
tcp.window_size_value == 0 Zero-window events
tls.handshake.type == 1 TLS Client Hello
ip.flags.df == 1 DF bit set
icmp.type == 3 and icmp.code == 4 PMTUD "fragmentation needed"

Useful capture filters (-f, BPF syntax — different from -Y!)

Filter What it captures
host 1.2.3.4 All traffic to/from that IP
tcp port 443 All HTTPS
tcp port 22 and host 10.0.0.5 SSH to that host
not arp Skip ARP noise
icmp ICMP only

curl

How it works (architecture)

curl is all userspace — no driver, no special privilege. Just sockets + TLS + a lot of protocol logic in libcurl. Verbose (-v) and trace (--trace-ascii) flags expose every layer's decision.

# Discard body, time the transfer
curl.exe -o NUL -s -w "DNS: %{time_namelookup}s  Connect: %{time_connect}s  TLS: %{time_appconnect}s  TTFB: %{time_starttransfer}s  Total: %{time_total}s  Speed: %{speed_download} B/s`n" https://example.com

# Download a fixed size for throughput testing (Cloudflare speed endpoint)
curl.exe -o NUL https://speed.cloudflare.com/__down?bytes=10000000

# HTTP/2 vs HTTP/1.1
curl.exe --http2 -o NUL -s -w "%{http_version}`n" https://example.com
curl.exe --http1.1 -o NUL -s -w "%{http_version}`n" https://example.com

# Force IPv4 / IPv6
curl.exe -4 https://example.com
curl.exe -6 https://example.com

# Show headers only
curl.exe -I https://example.com

# Verbose TLS handshake
curl.exe -v https://example.com 2>&1 | Select-String -Pattern "SSL|TLS|subject|issuer"

ping (Path MTU probing)

How it works (architecture)

tracert sets TTL=1,2,3,… and reads back ICMP "Time Exceeded" from each hop. ping -f -l N sets DF and watches for ICMP "Fragmentation Needed" — same protocol family, different sub-type.

Standard ping

ping example.com
ping -n 20 example.com          # 20 echoes
ping -t example.com             # continuous (Ctrl+C to stop)

Path MTU discovery — the binary search

# DF=1, payload size 1472 → total 1500 → should succeed on Ethernet
ping -f -l 1472 8.8.8.8

# DF=1, payload size 1473 → total 1501 → should fail
ping -f -l 1473 8.8.8.8
# Expect: "Packet needs to be fragmented but DF set."

# Binary-search the path MTU
ping -f -l 1400 host    # try lower
ping -f -l 1472 host    # try standard
# Largest size that succeeds + 28 (IP+ICMP overhead) = path MTU
Flag Meaning
-f Set Don't Fragment bit (DF=1)
-l <size> Payload size in bytes
-n <count> Number of echoes
-w <ms> Per-reply timeout

tracert / traceroute

How it works (architecture)

Why it works: every router decrements TTL by 1 and drops the packet (sending ICMP type 11) when TTL hits 0. By sending probes with TTL=1, 2, 3, … each hop introduces itself. Last hop responds with Echo Reply / Port Unreachable instead of TTL Exceeded — that's how tracert knows it reached the end.

# Standard
tracert example.com

# No DNS lookup, faster
tracert -d example.com

# Max 15 hops, 1s timeout
tracert -h 15 -w 1000 example.com

# Hop-by-hop with packet loss stats (better tool: pathping)
pathping example.com

netsh (Windows TCP tuning)

How it works (architecture)

netsh interface tcp set global autotuninglevel=normal and Set-NetTCPSetting -SettingName InternetCustom -AutoTuningLevelLocal Normal are two doorways to the same kernel-side TCP template.

⚠️ Most of these need an elevated PowerShell.

Inspect global TCP settings

netsh interface tcp show global

Look for Receive Window Auto-Tuning Level — the long-haul fix would change this.

Tune TCP (admin)

# Aggressive auto-tuning of receive window
netsh interface tcp set global autotuninglevel=normal       # default
netsh interface tcp set global autotuninglevel=experimental # max
netsh interface tcp set global autotuninglevel=disabled     # OFF (long-haul-like state)

# Show current per-interface MTU
netsh interface ipv4 show subinterfaces

# Set MTU on an interface (admin)
netsh interface ipv4 set subinterface "Ethernet" mtu=1400 store=persistent

Built-in packet capture (admin, no Wireshark needed)

# Start a trace (writes .etl)
netsh trace start capture=yes tracefile=C:\temp\net.etl

# Stop it
netsh trace stop

# Convert .etl to .pcapng (requires Microsoft.etl2pcapng)
etl2pcapng C:\temp\net.etl C:\temp\net.pcapng

PowerShell Get-NetTCP*

How it works (architecture)

Why two ways (netsh and Get-NetTCP*): they're alternate doorways to the same kernel state. PowerShell cmdlets go through MI/WMI providers; netsh goes through netshell helper DLLs. Both ultimately twiddle the same TCPIP.sys parameters. Modern best practice = PowerShell cmdlets (object output, scriptable). Legacy guides still use netsh because it predates the cmdlets.

# All TCP global parameters
Get-NetTCPSetting

# Show specific template (Internet, Datacenter, etc.)
Get-NetTCPSetting -SettingName Internet | Format-List *

# All TCP connections
Get-NetTCPConnection

# Connections to a specific remote port
Get-NetTCPConnection -RemotePort 443

# All listening ports + owning process
Get-NetTCPConnection -State Listen | Select-Object LocalPort, OwningProcess

# Per-connection RTT and bytes in flight (Win10+)
Get-NetTCPConnection -RemotePort 443 | Select-Object LocalPort, RemoteAddress, State

# Change auto-tuning level (admin)
Set-NetTCPSetting -SettingName Internet -AutoTuningLevelLocal Normal

iperf3 (throughput testing)

How it works (architecture)

iperf3 does not need Npcap — it generates traffic, doesn't capture it. Pair it with pktmon or Wireshark on the side to observe what iperf3 is producing.

Install:

winget install iperf3

Server (one machine)

iperf3 -s              # listen on default port 5201
iperf3 -s -p 9999      # custom port

Client (the other machine)

# Basic 10-second TCP test to server at 1.2.3.4
iperf3 -c 1.2.3.4

# 30 seconds, parallel streams
iperf3 -c 1.2.3.4 -t 30 -P 4

# 🎯 Reproduce the long-haul issue — tiny window
iperf3 -c 1.2.3.4 -w 16K -t 30

# Compare with bigger window
iperf3 -c 1.2.3.4 -w 4M -t 30

# JSON output (for scripting)
iperf3 -c 1.2.3.4 -t 10 -J > result.json

# UDP test instead (set rate)
iperf3 -c 1.2.3.4 -u -b 100M

# Reverse direction (server sends, client receives)
iperf3 -c 1.2.3.4 -R
Flag Meaning
-c <host> Client mode, target host
-s Server mode
-t <sec> Test duration
-w <size> Socket buffer / TCP window size 🎯
-P <n> Parallel streams
-R Reverse (server→client)
-u UDP
-b <rate> Target bandwidth (UDP)
-J JSON output

The cross-region reproduction: run two iperf3 -c against the same server, one with -w 16K and one with -w 4M. The latency difference (RTT × bandwidth) will be visible immediately.

pktmon (Windows built-in capture)

How it works (architecture)

Why pktmon and Npcap don't conflict: they both register as NDIS Lightweight Filters at different altitudes, so frames are observed by both. You can run a pktmon trace while Wireshark captures the same NIC.

⚠️ Requires admin. Modern Windows 10/11 / Server only.

# List interfaces
pktmon list

# Quick capture, in-memory ring
pktmon start --capture

# Stop
pktmon stop

# Convert latest log to pcapng
pktmon etl2pcap PktMon.etl -o capture.pcapng

# Filter by port (before start)
pktmon filter add web -p 443
pktmon filter add ssh -p 22
pktmon filter list
pktmon filter remove

# Live console output
pktmon start --capture --log-mode real-time

Use this when you can't install Npcap (no admin → install fails, but pktmon ships in-box).

etwdump (Wireshark's ETW source)

How it works (architecture)

etwdump is a small extcap plugin shipped inside the Wireshark install directory (C:\Program Files\Wireshark\extcap\etwdump.exe). It lets tshark/Wireshark consume Event Tracing for Windows (ETW) events as if they were packets — so even without Npcap you can still see something on the interface list.

  • It does not need Npcap.
  • It reads ETW providers (e.g., Microsoft-Windows-NDIS-PacketCapture) and converts events into a synthetic pcap stream.
  • Always appears as the interface line etwdump (Event Tracing for Windows (ETW) reader) in tshark -D.
# Confirm it's present
tshark -D | findstr etwdump

# Open the wizard in Wireshark GUI:
#   Capture → Options → "Manage Interfaces" → External Capture tab → etwdump → gear icon
# CLI usage (capture from an ETW .etl file already collected):
tshark -i etwdump --extcap-interface=etwdump `
  --etwfile "C:\path\to\PktMon.etl" -w from-etl.pcapng

# Live ETW: requires admin + a provider that's already running (e.g. via pktmon or logman)
logman create trace netcap -p Microsoft-Windows-NDIS-PacketCapture -o C:\temp\netcap.etl -ets
logman stop netcap -ets
tshark -i etwdump --etwfile "C:\temp\netcap.etl" -w netcap.pcapng

Verdict: etwdump is the graceful fallback when Npcap isn't installed — you lose true live capture and BPF filters, but you can still post-process Microsoft's own ETW packet traces inside Wireshark's UI.

netstat / Get-NetTCPConnection

How it works (architecture)

Why owning PID is sometimes blank without admin: AFD's per-socket process tag is privileged metadata. netstat -ano reads the snapshot of the kernel's TCB/UDB tables via GetExtendedTcpTable(TCP_TABLE_OWNER_PID_ALL). No packets are captured — just the connection control blocks.

# All connections + owning PID
netstat -ano

# TCP only
netstat -ano -p tcp

# Listening ports + processes (preferred PowerShell way)
Get-NetTCPConnection -State Listen | Sort-Object LocalPort | Format-Table LocalPort, OwningProcess, @{Name='Process';Expression={(Get-Process -Id $_.OwningProcess).Name}}

# Show interface stats (errors, discards)
Get-NetAdapterStatistics

nslookup / Resolve-DnsName

How it works (architecture)

Why nslookup and Resolve-DnsName can disagree: nslookup skips the Windows DNS Client cache entirely and queries the configured server directly. Resolve-DnsName (and every regular app via GetAddrInfo) goes through the cache + HOSTS file + the dnscache service first. To force a fresh query through the same path apps use: Resolve-DnsName -DnsOnly or Clear-DnsClientCache first.

# Basic
nslookup example.com

# Specific record type
nslookup -type=AAAA example.com           # IPv6
nslookup -type=MX gmail.com               # Mail
nslookup -type=TXT example.com            # TXT

# Query a specific resolver
nslookup example.com 1.1.1.1

# PowerShell-native (more parseable)
Resolve-DnsName example.com
Resolve-DnsName example.com -Type AAAA
Resolve-DnsName example.com -Server 8.8.8.8

Linux-only goodies worth knowing

# Live TCP stats per connection (RTT, cwnd, retrans)
ss -tin

# Watch socket-buffer high-water marks
ss -tem

# Show kernel TCP tuning
sysctl net.ipv4.tcp_wmem    # send buffer min/default/max
sysctl net.ipv4.tcp_rmem    # receive buffer min/default/max
sysctl net.ipv4.tcp_congestion_control

# Simulate latency on an interface (for long-haul repro on one box)
tc qdisc add dev eth0 root netem delay 180ms
tc qdisc del dev eth0 root

🧭 Recipe — "Is my throughput window-limited?"

  1. Measure RTT: ping <host>
  2. Capture a transfer: powershell tshark -i 5 -f "host <host>" -w bw.pcapng curl.exe -o NUL https://<host>/big-file
  3. Look for window-full: powershell tshark -r bw.pcapng -Y "tcp.analysis.window_full" | Measure-Object
  4. Compute theoretical max: window_bytes / RTT_sec
  5. If actual ≈ theoretical max but ≪ link speed → window-bound (long-haul pattern).
  6. Fix: enable auto-tuning or bump app's SO_SNDBUF.

🧭 When to pick what — tool decision matrix

Need Best tool Why
Live capture, BPF filters, dissection Wireshark + Npcap True kernel hook + rich UI
Capture on locked-down box, no admin install pktmon (in-box) → etl2pcap → Wireshark Ships with Windows
Read an .etl someone sent you tshark via etwdump No Npcap install needed
Reproduce throughput problem iperf3 + pktmon side-by-side Generator + observer
Verify PMTUD / ICMP path ping -f -l N, tracert Direct ICMP probes
